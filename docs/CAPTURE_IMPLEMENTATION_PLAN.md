# 即時畫面擷取實作計畫：第二輪修正與驗收

更新日期：2026-09-24。初版實作提交 `3077abb`，已由 `d6ea36a` 合併至 `main`。本輪狀態：R1–R4 程式修正與回歸測試完成；同一 AVD 的像素、方向、取消、停頓及負載部分實測完成，真實 inactive／斷線仍待驗證；性能目標未達。數據與剩餘限制見 [MEASUREMENTS.md](MEASUREMENTS.md#2026-09-24-第二輪窗口修正與-avd-重測)。

本文件取代初版待實作清單，作為下一個開發任務的要求。gRPC 擷取原型已可運作；量測與故障處理尚有四項已重現問題，且性能未達研究目標。合併不代表擷取後端已通過即時遊玩驗收。

## 1. 目標與邊界

依序完成：修正量測窗口 → 修正事件式串流健康狀態與時間跳動 → 建立回歸測試 → 重跑基準 → 依證據改善性能及評估替代後端。

- 保留即時 pixels 為唯一遊戲決策來源，不讀譜面、遊戲記憶體、存檔或預錄按鍵序列。
- 擷取只發布最新 frame；接收、轉換、日誌與下游所有緩衝皆須有上限，不回放過期影格。
- 所有主機端期限、耗時與統計窗口使用同一 monotonic clock；CPU process time 僅用於同一窗口的資源消耗統計。Unix 來源時間不作可信的主機延遲或觸控時機基準。
- 本輪範圍是 Capture、Session 的擷取健康狀態、CLI、測試、fixture、量測及相關文件。觸控注入、Phigros 辨識、深度學習、自動選曲與 Predictor 演算法改造均不在範圍。
- 保留 ADB 診斷、合成閉環及可選 gRPC 依賴。來源／認證設定明確指定，權杖不輸出至日誌；不關閉認證、不清除 AVD 或遊戲資料。
- 開始前閱讀 `AGENTS.md`、`README.md`、`docs/ARCHITECTURE.md`、`docs/ROADMAP.md`、`docs/CAPTURE_AND_VISION_RESEARCH.md`、`docs/MEASUREMENTS.md` 及本文件。

## 3. 必修 R1：就緒、暖機與正式量測分開

位置：`src/pas/cli.py::grpc_capture_bench`。目前在來源建立與首次有效影格之前決定正式起訖時間，初始化可能吃掉暖機甚至正式窗口。

已重現：`measurements/grpc_fixture_load/capture.jsonl` 宣告 30 秒正式量測，但 178 張正式樣本僅跨 11.5515509 秒，第一張來源影格即為正式樣本；另以延遲假來源重現零張影格仍回傳 `capture_error=null`。

要求：

1. 明確定義 `CONNECTING → WARMUP → MEASURING → STOPPING` 及失敗／取消狀態。來源與必要依賴初始化、認證、首張有效圖的時間獨立記錄，不算進暖機或正式量測。
2. 就緒後完成設定的暖機，再以主機 monotonic 開始完整正式窗口。持續串流不因切換窗口重新連線；窗口邊界、設定秒數、實際秒數及完成狀態写入 JSONL。
3. 建立可配置的就緒期限。零張有效圖、所有圖無效、連線失敗、無法證明有效動態來源等情況須標成失敗／未完成，不可出現看似成功的零樣本性能報告；CLI 狀態與退出碼應一致。
4. 分開報告「正式牆鐘窗口（monotonic）」、「首末有效影格跨度」與「無影格停頓」。正式窗口内停頓是待量測現象，不得事後縮短分母美化 FPS；相反，初始化不應算入穩態 FPS。
5. 負載是受控實驗配置，明確記錄何時啟用，避免把首次 import 的 GIL 競爭當作持續接收性能。

驗收：可控延遲來源、超過就緒期限、零／一張圖、首張遲到、暖機與正式邊界、測量中停頓均有測試。延遲初始化後仍得到完整暖機與正式窗口，或清楚因就緒超時失敗。

## 4. 必修 R2：所有資源與計數使用一致窗口

位置：`src/pas/cli.py::grpc_capture_bench`。目前 CPU 在暖機前累積、清理後才結算，卻除以正式 duration；來源跳號與未消費覆蓋等是整段生命週期累積值。

要求：

- 在正式起訖時取得 CPU process time 與各累積計數的可一致讀取快照。CPU 百分比使用相同窗口的 CPU 差值／實際主機 monotonic 時長，不包含暖機、停止、圖片輸出或清理。
- 來源跳號、相對舊圖丟棄、invalid／inactive、應用覆蓋、consumer skips 各自定義邊界；正式窗口值與全程值分開命名，不互相相加。
- 精確說明跨邊界的 frame／序號跳躍歸屬；採一致的半開區間。接收、發布、消費在邊界附近可能不同，須能由原始事件核對，而非強求所有數目相等。
- 記錄兩端快照及足以重算的事件；RSS／CPU 缺測須標示未知。保持日誌串流寫入，長測避免累積無上限的事件／影像；百分位數若離線計算或近似估計需揭露方法。
- 對歷史 `MEASUREMENTS.md` 的受影響 CPU／負載結論加上更正；未保存 CPU 窗口快照的舊資料不得臆造修正值，只能重測。

驗收：以注入的 clock／CPU counter、暖機期間額外 CPU／跳號／覆蓋及清理期間成本，證明它們不污染正式統計。報告能由 JSONL 重算，改變暖機長度不會按比例虛增相同穩態 CPU 使用率。

## 5. 必修 R3：事件式串流健康與畫面新鮮度分離

位置：`src/pas/session.py::monitor_for`，以及 gRPC source／worker 的健康資訊。現在 `event_driven=True` 完全豁免 stale；只交付一張後永久等待的來源可一直留在 `NAVIGATING`。

要求：

- 區分傳輸已連線／可回應、來源 active／inactive、最後有效圖時間與畫面新鮮度。`channel connected` 不能代表畫面仍然有效，健康探測也不能把舊圖當新圖。
- 正常靜態畫面不應每隔一秒無條件報錯；但無法確認的來源也不能無限保有「擷取正常」狀態。採有期限的健康探測或明確 `UNKNOWN`／degraded 狀態與停止條件；狀態名稱可依既有設計調整。
- 若協定無法區分靜止與卡住，明確記錄此可觀測性限制，保守撤銷新鮮度資格。不能用 ADB 的遊戲內部資料推斷畫面狀態。
- 健康檢查不得阻塞擷取、建立影格佇列、增加偽造的序號或刷新原圖時間戳。所有期限用主機 monotonic。
- 停止、inactive、RPC 失敗和來源失去進展皆有明確原因及可取消路徑。未確認的新鮮度不得被未來的遊玩門控當作可用輸入；本輪不啟用觸控。

驗收：正常靜態且健康、靜態但無法驗證、只送一張後阻塞、inactive→active、明確斷線、使用者取消均以假來源驗證。不可單純刪除靜態支援來讓測試通過；停止仍須在 2 秒目標內完成並回收資源。

## 6. 必修 R4：時間不連續不得造成無限丟圖

位置：`src/pas/capture_grpc.py` 的 `max_relative_lag_ms`。目前永久以第一張為錨點；模擬來源 Unix 時間倒退 1 秒後，後續四張正常前進的影格全被丟棄。

要求：

- 來源 Unix metadata 與主機 monotonic 必須保持時域標記；相對差值之差僅是未校準診斷訊號，不提升為絕對來源年齡或唯一的健康／排程依據。
- 檢查時間戳倒退、大幅前跳、缺失、停止前進及來源 generation 變化。遇到不連續，應明確標為不可信並停止／要求重新建立來源，或透過有證據的校準重新建立基準。
- 禁止每次落後就重新設錨，這會把真實积壓洗掉。若採重新校準，必須有獨立條件證明已恢復當前串流；沒有條件時採明確失敗。
- 新鮮度保護還須有主機 monotonic 的最大無發布／最大丟棄持續時間，確保不會無限吞圖而下游永久保有舊圖。
- 保持首次接收前的未知來源延遲為未知；對時鐘速率漂移與未知 metadata 不宣稱精確同步。

驗收：正常排隊舊圖、來源倒退 1 秒、前跳、零值／缺失、凍結時間、長期漂移、序號重置、連續丟棄及停止都可重現。必須同時證明不會默默永久丟圖，也不會因重新設錨接受整批積壓圖。

## 7. 修正後的實測與性能工作

### 必做批次

- 同一 AVD 原生 1280×720 fixture：就緒後暖機 10 秒、正式 60 秒，正常至少 3 批。每批保存獨立 run ID、版本／commit、環境、完整命令、原始 JSONL 及雜湊。
- consumer 延遲 50／100 ms、15 秒後恢復，以及接收端暫停 500 ms（保護停用／啟用）各跑可比較批次，清楚報告窗口、可見計數與恢復時間。
- 至少重跑一批受控 CPU 負載；將同程序 GIL 競爭與主機／AVD 負載分開描述，不把它們視為同一種壓力。
- 實際 AVD 可用時驗證靜態、取消、inactive／斷線與可安全進行的尺寸／方向改變；不能為測試清除資料或打斷登入。必要的使用者操作集中提出，其餘工作先完成。
- 各分布至少報 n、p50／p95／p99／最大值、失敗、各類丟棄和缺測項。絕對來源年齡無可靠時鐘映射時仍標未知。

### 性能診斷順序

1. 先確認 fixture 的實際更新率；量測擷取開啟前後的差異時，只使用受控測試應用的離線真值或可見標記，不讀遊戲內部狀態。
2. 比較最小接收、開啟轉換、開啟 fixture 解碼／日誌等受控條件，以分解 Emulator 產生／讀回、gRPC／protobuf、像素複製、Python／GIL 與日誌成本；新增探針也須揭露自身成本。
3. 640×360 可用於成本診斷，但不得拿縮圖結果替代 1280×720 驗收。RGB888 優先，RGBA 成本另列。
4. 有明確瓶頸證據後才作必要優化；改善後以相同窗口、fixture 與負載比較，不能只報平均 FPS。
5. 一般 gRPC 仍不適合時才評估下一個有理由的候選。MMAP 必須驗證一致性／撕裂與資源生命週期；WGC 必須處理視窗、readback、座標及合成器時戳；scrcpy 必須維持相依壓縮資料正確解碼，只丟棄下游已解碼舊圖。不得一次無條件實作所有後端。

研究目標維持：確認約 60 FPS 的動態來源下，1280×720 接收至少 55 個不同畫面／秒，到達間隔 p95 ≤33.4 ms、p99 ≤50 ms；受控停頓後 100 ms 內恢復較新圖，無持續積壓。這些不是遊戲判定窗。來源達不到 60 FPS 時須回報瓶頸與條件未滿足，不能宣稱擷取達標；不得為通過驗收調低門檻。

## 8. 交付與完成定義

1. R1–R4 全部修正並有失敗可重現、修正後通過的回歸測試；安裝及未安裝 gRPC extras 的既有功能均通過適當檢查。
2. 更正後的完整正式窗口基準、原始資料及可重算摘要，清楚區分歷史有效數據、歷史有偏差數據與新實測。環境不可用時仍完成獨立測試，實測項維持待驗證。
3. `README.md` 更新新參數／狀態／故障說明；`ARCHITECTURE.md` 更新時間、健康與資料契約；`ROADMAP.md`、`MEASUREMENTS.md` 與研究文件同步更新結論。
4. 報告分開回答「程式可靠性修正完成」、「實機功能驗證完成」、「性能研究目標達成」；不得以測試全綠等同三者都完成。
5. 性能不足時，交付定位證據、已嘗試的受控改善與下一個具體候選理由；不跳往觸控／遊戲辨識，也不承諾尚無證據的成績。

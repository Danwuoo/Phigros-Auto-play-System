## 音符與觸控語義

| 音符 | 基本操作 | 主程式推導出的需求 |
| --- | --- | --- |
| Tap／藍鍵 | 在時機到達時點擊 | 需要新的 down；一根已按住的手指不能當作連續 Tap |
| Hold／長條 | 準時按下，持續覆蓋判定區域直到結束 | 分開管理頭部觸發、持續覆蓋、尾部結束；保持期間仍須更新位置 |
| Drag／黃鍵 | 在判定時機有手指接住 | 可以預先建立接觸；是否移動取決於區域變化，不是每顆都點一下 |
| Flick／紅／粉鍵 | 在區域內向任意方向滑動 | 規劃具有持續時間、位移與速度的接觸軌跡，不能只更新一次座標 |

玩家原創教學區分上述四種操作，並記錄 Tap 有 Perfect／Good／Bad／Miss，Hold 無 Bad，Drag／Flick 僅 Perfect／Miss；也描述突然變速與混合速度配置。[音符與變速教學](https://www.bilibili.com/opus/492666537367388118)

社群補充：Hold 尾部不要求準時放開，可換指；連續 Flick 不能假設同方向持續滑動會不斷重新觸發。重疊 Tap／Hold 頭部可能需要多次獨立觸發，重疊持續區域則可能共用接觸。以上細節須逐項驗證。[操作與重疊音符說明](https://wikiwiki.jp/phigros/howtoplay)

**設計推論：** Note ID 與 contact ID 必須分開。一顆 Hold 可跨接觸點交接，一根手指也可能覆蓋多個有效區域。初版可採保守分指策略，但資料模型不能把兩者永久綁死。對 Flick 的方向反轉、重新接觸、最小速度及連發重置，保留可測參數，不自行填入毫秒或像素常數。

## 判定區域與多判定線

垂直判定是沿「相對於該判定線的法線方向」延伸，並非永遠沿螢幕 Y 軸。玩家的圖解說明：觸控點向對應線的垂足落在音符判定位置即可；也指出額外點按可能誤觸附近 Tap。[玩家原創垂直判定圖解](https://www.luogu.com/article/dy1z6aaf)

社群資料描述多條線、線的平移／旋轉／隱藏、裝飾線，以及以音符重合呈現時機的配置；並指出顯示音符寬度與判定區域不是同一件事。該頁本次直接開啟受限，僅取得搜尋索引節錄，證據強度低於完整頁面與本機操作驗證。[遊戲內容](https://phigros.fandom.com/zh/wiki/%E6%B8%B8%E6%88%8F%E5%86%85%E5%AE%B9?variant=zh-hk)

**建議的幾何抽象（本專案設計，非遊戲原始碼公式）：** 對線的切向單位向量 `u(t)`、音符預期落點 `p(t)`，候選觸控點 `q` 可表示為：

```text
q 位於可觸控畫面內
abs(dot(q - p(t), u(t))) <= w
```

`w` 是待校準的區域半寬，不直接取可見 Note 寬度。實作還需扣除暫停按鈕、邊界手勢等不宜操作區域。預測的時機與可選觸控區域應分開輸出，供動作規劃器選擇衝突少、移動短的落點。

多線場景不能只採最近線段配對：用 Note 朝向、相對運動、歷史對應與線的可見度保留候選關聯。裝飾線不能因長得像線就獲得操作資格。多個重疊候選不能在辨識階段直接合併成一顆音符。

## 時間、分數與介面變化

| 項目 | 本次查到的證據 | 開發處理 |
| --- | --- | --- |
| 普通 Perfect | 歷史官方 Q&A 為 ±80 ms | 作研究參考；不等於容許擷取延遲 80 ms |
| 課題模式 | 玩家指南描述 Perfect ±40 ms、Good ±75 ms，三曲連續，無普通連擊分 | 模式與時序設定分離；曲間重新確認狀態 |
| 普通 Good／Bad | 來源有 150／160 ms 等分歧，Bad 邊界也不一致 | 不確立單一數字；正負方向分別實測 |
| Hold 寬限 | 社群提及容許短暫離開／提早放開，但數字和語義不齊 | 初版維持覆蓋，不利用未驗證寬限 |
| Flick／Drag 時窗 | 不能從「只有 Perfect／Miss」推出與 Tap 使用同一窗口 | 單獨測試提前、延後、預先接觸與動作重置 |

課題與普通模式差異、章節／難度解鎖、Data、收藏品和特殊解鎖流程均見玩家指南。特殊流程甚至有零分卻出現虛假 φ 的演出，因此畫面單一評級符號不能作為自動操作成功的唯一證據。[玩家入坑指南](https://www.taptap.cn/moment/31427787847894330?share_id=64ece1a83619)

AP 表示全 Perfect，FC 允許 Good；Bad／Miss 斷連。可選 FC/AP 指示器會改變判定線顏色。因此線的顏色只能是輔助特徵，不能把白色視為唯一有效線。[玩家 AP／FC 說明](https://www.taptap.cn/moment/232548387734424114)

**設計推論：** 驗收記錄結果畫面的 Perfect／Good／Bad／Miss、ACC、最大連擊及可見 Early／Late；分數和 RKS 不參與下一顆音符的排程。Note 消失也可能是漏失或遮擋，不能直接算命中。開局保存可見設定：Note 大小、背景亮度、打擊特效、多押提示、FC/AP 指示、鏡像、模式與延遲調整；本次未進入設定確認這些值。

## 可見性與預測的限制

以下是由前述機制導出的工程要求，不是本次已完成的功能：

1. 固定水平線的距離／速度公式僅保留作 Fixture 基線。遊戲版本需估計 Note 與所屬線的相對運動，線與 Note 均可能改變速度。
2. 短期預測隨每張新圖更新；位移不連續、速度突變或配對不明時，提高不確定度，縮短預測期限或撤銷尚未送出的動作。
3. 判定線暫時不可見不等於離開遊玩畫面。UI 狀態判定與幾何可觀測性分離：有有效視覺證據的其他目標仍可處理，無證據的目標不猜按。
4. 純 pixels 在某些突然出現、完全遮蔽或隱藏配置下可能沒有足夠預告資訊。須記錄「不可觀測／預告時間不足」，不能以歌曲名稱查表或離線譜面補足。不能在開發前承諾全曲全難度 AP。
5. 線姿態、音符類型／數量、接觸狀態、時機預測四種不確定性分開保留，避免單一 confidence 掩蓋錯配。
6. 遊戲語義中的 Hold 維持與 Flick 更新仍須服從停止、斷線、過期門控；失去觸控後端時，釋放只能記為嘗試，不能假報已放開。

## 對現有程式的具體影響

| 現況 | 下一版需要補上的內容 |
| --- | --- |
| `Observation` 是單點 | 多 Note／多線集合、類別、朝向、可見度與候選對應 |
| `VelocityTracker` 是單目標短期估速 | 多目標身分、線關聯、遮擋與運動突變處理 |
| `LineCrossingPredictor` 為固定 `line_y` | 動態線局部座標、有效區域、預測期限與可觀測性 |
| `HitIntent` 只有一個時間與座標 | 分開撞線估計、觸控窗口、持續覆蓋／滑動需求與依據 |
| `Scheduler.submit()` 一律生成 Tap down/up，contact ID 使用 track ID | 新增動作規劃層與 contact allocator；排程器執行已確認的接觸計畫 |
| 現有 Session 沒有 PLAYING 分類器 | 視覺接手、暫停／恢復／結算、場景切換及 epoch 隔離 |

這些都是設計需求，不代表契約已變更。底層擷取與注入維持遊戲無關；只有遊戲層了解上述音符語義。

## 驗證順序與待辦

1. **觸控 Fixture：** 獨立指 ID、同時 down、持續 hold 加另一指 tap、move、方向反轉、交錯 up、停止釋放；以可見回饋確認並保存設定。
2. **簡單目標閉環：** 用已知且可重現的動態像素目標，驗證預測／排程、負載下丟棄舊圖、注入與可見效果時間。測試真值僅供離線評估。
3. **遊戲只觀察：** 使用者手動選曲；建立四類 Note、多線、重疊、變速、線消失等畫面樣本與人工標註，不以錄影回放決策。
4. **遊戲受控驗證：** 逐項測四類動作、垂直判定、區域寬度、Flick 重置、Hold 維持與多押；先保守處理，驗證後才利用共用接觸等特性。
5. **特殊場景：** 暫停恢復、無音符間奏、非白線、鏡像、隱藏線、突然變速、演出假畫面與課題曲間轉換。未解鎖內容不得標為已驗證。

所有時序結果保留版本、解析度、設定、後端、負載、樣本數與分布。網路時間窗、擷取到達間隔和主機注入返回均不能單獨證明遊戲實際判定精度。依 ROADMAP 完成前兩項，再進入遊戲專用實作與驗收。
